# Baseline: concurrent assignment-wave scaling, 2026-08-28

Reproduction of the current-main zero-cache latency diagnosis (rocicorp/mono
`ac5eb231`, 2026-08-27) on this fork's `main`. Raw per-client samples and per-N
medians are in `summary.json`; per-client replay output is in `raw/`.

**The scaling law reproduces.** Query-wave wall time grows near-linearly with
concurrent client groups while per-group CPU-ish query time stays flat, so the
limit is queueing on one sync worker's event loop and not the cost of any single
group's work. One divergence is recorded below: the tracker graph is about 2.4x
cheaper here than in the diagnosis, which moves its share of per-group processing
from ~73% to ~53%.

## Wave shape

Every run of every N asserts wave integrity and all 93 client samples passed:
completion spread across the six roots was 0 ms in every case, which is what one
group poke plus `pokers.end(finalVersion)` should produce. `queryCount` is 8 in
every `diagnosis-query-wave-stages` event, six requested roots plus `lmids` and
`mutationResults` for the fresh client group. Row counts match the diagnosis
exactly: `assignment.basic` 5, `assignment.roster` 1,118,
`assignment.with_problems` 53, `problem_trackers.for_assignment` 7,768.

## The tracker divergence

Five of the six roots land within 26% of the diagnosis on this machine, and four
of them within 10%. Only `problem_trackers.for_assignment` differs, and it differs
by 2.4x in the cheap direction. Hardware cannot explain that: a faster machine
would move every query, and `assignment.basic`, `assignment.roster` and
`misconduct.for_assignment_count` all reproduce almost exactly.

The query is byte-identical to the diagnosis run. Its `transformationHash` is
`216mzlo8m5qcv` in both, its `queryHash` is `37lvijakf37kg` in both, and it emits
the same 7,768 lifecycle row events. So the AST, the transform and the row set
touched are the same; only the per-row cost differs, 26 µs here against 69 µs
there.

Two data-shape explanations were tested against the diagnosis replica and both
were ruled out:

1. **Background problem catalog.** The diagnosis replica held 20,327 rows in
   `problem` where the fixture alone gives 27, and the tracker query resolves one
   problem per tracker. Rebuilding the catalog to 20,327 rows with matching
   payload sizes (avg 377 vs 357 bytes of text, 869 vs 856 bytes of gxml) moved
   tracker share from 52.1% to 52.5%.
2. **Denser access graph.** The diagnosis replica had 23 classes, 17 teachers,
   22 `teacher_to_class` and 160 `student_class_membership` rows against this
   database's 9 / 10 / 8 / 139. Matching those counts made the *light* queries
   more expensive (`assignment.basic` 27 → 53 ms, `assignment.summary` 34 → 63 ms)
   while the tracker query stayed at 224 ms, pushing tracker share down to 45.7%.

Both experiments were reverted; the numbers above are from the plain fixture.

The third candidate was the zero-cache code itself, and it was tested directly.
The diagnosis commit `ac5eb231` is fetchable from the fork remote even though no
branch contains it, and its parent is exactly `7fb2c78`, the upstream tip that
fork `main` merges. The entire delta between the two bases is one commit, #6425,
which touches `litestream3-prometheus-poller.ts` and its test — 35 lines in a
metrics poller that does not run in this harness.

Both bases were built with the same instrumentation and run side by side on
their own port, app id and replica against the same database, six measured N=1
replays each, alternating and with both instances warm:

| query | A: `16019afa4` | B: `ac5eb2311` | B / A | diagnosis |
|---|---:|---:|---:|---:|
| `assignment.basic` | 31.7 | 33.7 | 1.06x | 21.3 |
| `assignment.summary` | 31.8 | 32.2 | 1.01x | 39.4 |
| `assignment.roster` | 42.5 | 51.4 | 1.21x | 49.8 |
| `assignment.with_problems` | 17.5 | 18.7 | 1.07x | 19.8 |
| `problem_trackers.for_assignment` | 190.4 | 231.5 | 1.22x | 537.7 |
| `misconduct.for_assignment_count` | 67.5 | 76.0 | 1.13x | 68.9 |
| per-group cpu | 391.2 | 447.8 | 1.14x | 730.6 |
| query wave | 480.7 | 546.9 | 1.14x | 818.2 |

The diagnosis commit shows no tracker-specific penalty. Its B/A of 1.22x sits
inside the same band as `assignment.roster` at 1.21x, and the whole column is a
flat ~1.14x offset from running two zero-cache instances on one 8-core box. What
it does show is `problem_trackers.for_assignment` at 231.5 ms on the exact
commit the diagnosis measured at 537.7 ms — 2.3x cheaper on this machine, with
the same instrumentation, the same fixture, and the same `transformationHash`.

So the divergence is a machine-dependent per-row constant on the one query whose
working set is large, not a code change. `problem_trackers.for_assignment`
hydrates 7,768 row events against at most 1,118 for any other root, so it is the
only root whose cost is dominated by cache residency and allocation rate rather
than by fixed per-query overhead; a different host memory subsystem moves it and
leaves the small roots roughly where they were. On the same commit, five of the
six roots land between 0.82x and 1.58x of the diagnosis while the tracker graph
lands at 0.43x.

The practical consequence for optimization branches: the scaling law and the
ratio columns are the portable result. Re-baseline the tracker-dominance figure
on your own hardware rather than carrying either ~73% or ~53% forward.

## Method notes and divergences from the diagnosis

- **Dedicated database.** The diagnosis seeded the shared goblins dev database.
  This run used `CREATE DATABASE zcbaseline TEMPLATE goblins`, so the schema is
  the real migrated one but the dev database was never written to. That is the
  source of the smaller background row counts discussed above.
- **Session tokens.** The exported seeder mints one `session` row with token
  `emu-session-token`, while the concurrency driver sends
  `emu-session-token-001`, `-002`, and so on. `apply-seed.sh` now mints one row
  per concurrent client. An unmatched token does not fail loudly: the transform
  endpoint answers 200 with `userID: null` and the connection is then rejected
  with "Connection userID does not match validated server userID", so every root
  times out with zero rows.
- **N=16 has 48 samples** here against the diagnosis's 32, because this run did
  three runs at N=16 where the diagnosis did two.
- **No CPU profile.** The diagnosis attached a profiler to the sync worker over
  the Node inspector. zero-cache forks its workers without per-child `execArgv`,
  so a `--inspect` flag is inherited by every child and they contend for port
  9229; there is no supported way to target syncer index 0 from this checkout.
  The scaling result does not depend on it.
- **Log level `info`.** Confirmed against the diagnosis server log, which has no
  debug-level lines. `debug` adds per-row logging that would distort exactly the
  intervals being measured.
